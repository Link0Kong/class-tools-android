# Round 60 报告 · v4.50.0（通知「无法全部加载」修复）

> 用户反馈：「优化通知无法全部加载的问题」。
> 背景：v4.47 已把通知改为「最新 20 条分页 + 加载更多」，但旧通知分页页大小固定 20 条，而云端旧页正文差异极大（单页可达 3–4MB），加上 HTTP readTimeout 仅 10s，慢网/大响应页会超时失败，用户无法把所有通知加载完。

## 根因（Lead 用测试身份实测）

- `notices?select=*` 全表约 **13.9MB**；按 20 条分页：第 1 页 ~0.55MB、第 2–3 页各 ~3MB、第 4 页 ~9MB。
- `OkHttpTransport` 原 readTimeout=10s、callTimeout=20s；仓库 30s 协程超时包不住底层 socket 超时；大页在移动网络下必失败。
- UI「加载更多」每次只拉一页，失败即止，因此永远加载不完。

## 修复

1. **加载全部语义**：通知列表底部「加载更多」改为「**加载全部（还有 N 条）**」，点击后连续按页加载直到全部完成（每页成功即更新列表、逐页出现新内容）；加载中显示「正在加载全部…（剩余 N 条）」；任一步失败停止并保留已加载内容，再点可继续/重试。
2. **自适应页大小**：仓库 `loadMore` 优先 5 条/页；若该页超时自动降级 3 条、1 条重试（旧通知单页 3–4MB 时保证可推进）；首屏仍 20 条快速出列表。
3. **超时放宽**：`OkHttpTransport` connect 15s / read 30s / write 30s / call 60s；通知仓库单请求协程超时 40s + 超时重试 1 次；其它仓库/接口保持原有逻辑。
4. 缓存/签名/去重/已读状态/长期通知/顶部数据卡等口径全部不变。

## 已知边界

- 旧通知总量约 100 条；首次点「加载全部」需要逐页下载旧正文（总数据约 14MB），慢网耗时较长但有进度文案、失败可继续，不会像旧版一样一页超时就卡死。
- 大页自适应靠超时触发；网络很快时仍按 5 条/页。
